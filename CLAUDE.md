# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Clean rebuild of zoominspect.com (Next.js 16 App Router + TypeScript +
Tailwind CSS v4), replacing the original WordPress site after it was
compromised with hidden SEO-spam injections. Content was hand-extracted
from the old site's HTML dumps and sanitized; see
`docs/superpowers/specs/2026-09-15-zoominspect-rebuild-design.md` for the
full design rationale and `docs/superpowers/plans/2026-09-15-zoominspect-rebuild.md`
for how it was built.

## Commands

```bash
npm install
npm run dev             # dev server
npm run build            # production build (also type-checks via tsc)
npm run start            # serve the production build

npm run test             # run the full Vitest suite once
npm run test:watch       # Vitest watch mode
npx vitest run path/to/file.test.ts              # single test file
npx vitest run -t "test name substring"          # single test by name

npm run lint              # ESLint
npm run check:safety      # scans app/, content/, components/, lib/, public/ for spam-injection patterns
```

`check:safety` must report clean, and `npm run build` must succeed,
before any content change is considered done — this is the project's
core invariant (see "Content safety scanner" below).

## Architecture

### Content model: static pages vs. MDX blog

- **Marketing pages** (`app/page.tsx`, `app/<service>/page.tsx`,
  `app/inspection-standards/page.tsx`, `app/contact/page.tsx`) are plain
  React components with content hardcoded inline — no CMS. All 9 service
  pages share `components/ServicePageLayout.tsx` (title + prose-wrapped
  children + a "Get A Quote" CTA to `/contact`).
- **Blog posts** live as MDX files in `content/blog/<slug>.mdx` with
  frontmatter (`title`, `date`, `excerpt`, `coverImage`), read at
  build/request time by `lib/blog.ts` (`getAllPosts()`,
  `getPostBySlug(slug)`) via `gray-matter`, and rendered through
  `app/blogs/[slug]/page.tsx` using `next-mdx-remote/rsc`. `lib/blog.ts`
  exposes `getAllPostsFrom(dir)`/`getPostBySlugFrom(dir, slug)` taking an
  explicit directory so tests can point at a fixture directory instead of
  the real `content/blog`.
- Blog post `date` values are **sequential placeholders** assigned during
  the content migration (2023-01-01 → 2023-02-07), not real original
  publish dates.
- `lib/siteData.ts` is the single source of truth for `SERVICES` (9
  entries: slug/name/priceLabel/description), `INDUSTRIES` (6 groups),
  `CONTACT_INFO`, and `NAV_LINKS` (the "Our Solutions" dropdown is
  derived from `SERVICES`, not duplicated). Consumed by `Header`,
  `Footer`, the home page, and the service-card grid.

### Content safety scanner

`lib/contentSafety.ts` (+ `scripts/check-content-safety.mjs`, run via
`npm run check:safety`) exists specifically to catch a recurrence of the
hack that compromised the original site: hidden Cyrillic/gambling spam
text and off-screen CSS-injection markup (`overflow:hidden` combined with
`position:absolute` at a large/negative offset). It scans `app/`,
`content/`, `components/`, `lib/`, and `public/` for these signatures.
`lib/contentSafety.ts`/`.test.ts` themselves are excluded from the scan
(they legitimately contain the spam keyword list and test fixtures that
would otherwise self-trigger it) via `EXCLUDED_FILES` in the scanner
script — if you touch the scanner's own keyword/regex list, remember this
exclusion exists.

### Tailwind v4 — no config file

This project uses Tailwind v4's config-less setup: there is **no**
`tailwind.config.ts`/`.js`. Theme tokens (including the brand colors
`brand-navy` #0B4F71, `brand-gold` #F5A623, `brand-orange` #F2871F) are
declared in the `@theme inline { ... }` block in `app/globals.css`, and
plugins are registered via `@plugin "..."` CSS directives (e.g.
`@plugin "@tailwindcss/typography";`) in the same file, not a JS plugins
array.

### Next.js 16 dynamic route params are async

Route segments/`generateMetadata` on dynamic routes (`app/blogs/[slug]/page.tsx`)
receive `params: Promise<{ slug: string }>` and must `await params` before
destructuring — this is a Next 16 API change from earlier versions;
`generateStaticParams` is unaffected since it receives no `params`.
`AGENTS.md` (auto-regenerated by `next dev`) points at
`node_modules/next/dist/docs/` as the source of truth for this installed
version's breaking changes — check it before relying on API shapes from
training data or older Next.js docs.

### Contact form

`components/ContactForm.tsx` posts JSON to `app/api/contact/route.ts`,
which sends mail via Nodemailer using `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/
`SMTP_PASS`/`CONTACT_TO_EMAIL` (see `.env.example`; real values are never
committed — set them in Vercel for production). The route has a hidden
honeypot field check, email-format/length validation, and a simple
in-memory per-IP rate limit (5 requests/60s, `requestLog` Map — resets on
redeploy/cold start, not persisted).

### Security headers

`next.config.ts` sets a CSP and other security headers. `script-src`
**must** include `'unsafe-inline'` — Next.js injects inline `<script>`
tags on every page to hydrate RSC flight data, and a stricter CSP breaks
hydration site-wide (this was caught and fixed once already; don't
tighten `script-src` without adding a nonce-based alternative and
verifying hydration still works in a real browser, not just via
`next build`).

## Testing conventions

Vitest + React Testing Library, jsdom environment (`vitest.config.mjs`).
Tests exercise real filesystem/DOM behavior rather than mocking
internals: `lib/blog.test.ts` uses real temp directories with real
`.mdx` fixtures, `app/api/contact/route.test.ts` mocks only `nodemailer`
at the boundary. Note: `Header.tsx` renders the same nav links in both
the desktop and mobile `<nav>` simultaneously (mobile hidden via CSS
class, not removed from the DOM) — `Header.test.tsx` scopes its queries
with `within(screen.getByTestId("desktop-nav"))` to avoid
testing-library's "found multiple elements" error; keep that scoping if
you touch the nav.
